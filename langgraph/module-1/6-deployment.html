LangGraph Deployment: Yerel Studio’dan LangSmith Deployment’a

Bu ders, notebook içinde geliştirilen araç kullanabilen ve state taşıyan bir LangGraph agent’ının yerel Studio API’si ve bulut deployment üzerinden aynı SDK arayüzüyle nasıl çalıştırıldığını açıklar.

Kapsam ve Bağlam

Bu bölümde amaç, önceki agent çalışmalarında kurulan act, observe, reason ve state kalıcılığı fikrini notebook sınırının dışına taşımaktır. Bir agent’ın notebook içinde çalışması pedagojik olarak yeterli olabilir; üretim açısından ise aynı graph’ın API olarak servis edilmesi, izlenmesi ve başka istemcilerden çağrılabilmesi gerekir.

Bu Dersin Ana Tezi

LangGraph deployment akışı, graph kodunu bir API yüzeyi olarak paketler; bu API yerelde Studio tarafından, bulutta ise LangSmith Deployment tarafından servis edilebilir. SDK tarafında temel kullanım deseni değişmez: istemci oluşturulur, assistant bulunur, thread açılır ve run stream edilir.

Bu nedenle dersin merkezinde yeni bir agent mimarisi kurmak değil, mevcut agent graph’ının yerel ve uzak çalışma ortamları arasında nasıl aynı programlama modeliyle çağrılabildiğini anlamak vardır.

Öğrenme Hedefleri

  • LangGraph kütüphanesi, LangGraph API, LangSmith Studio, LangSmith Deployment ve SDK arasındaki görev ayrımını açıklamak.
  • Yerel Studio API’sine get_client ile bağlanıp yayınlanan assistant kayıtlarını listelemek.
  • thread, assistant, run ve stream_mode kavramlarını deployment bağlamında ilişkilendirmek.
  • Bir agent run’ının stream çıktısında insan mesajı, tool çağrısı, tool sonucu ve nihai AI cevabını ayırt etmek.
  • Yerel API URL’i ile bulut deployment URL’i arasında SDK kullanım deseninin neden değişmediğini göstermek.
  • API anahtarını kaynak koda yazmadan ortam değişkeni üzerinden hazırlamak.

Ön Koşullar

  • Python fonksiyonları, dictionary/list yapıları ve async for sözdizimini okuyabilmek.
  • LangGraph’ta agent graph, tool call, state ve reducer fikrine temel düzeyde aşina olmak.
  • Yerel geliştirme sunucusu, API URL’i ve ortam değişkeni kavramlarını bilmek.
  • Bulut deployment için API anahtarının kod içine yazılmaması gerektiğini anlamak.
Sürüm Notu

Materyalde belirli bir LangGraph veya LangSmith SDK sürümü açıkça belirtilmiyor. Bu nedenle anlatım, görünen API kullanımlarına ve kavramsal akışa bağlı tutulmuştur.

Ana Anlatım

Notebook’tan API’ye Geçiş

Önceki agent örneklerinde model tool çağrısı üretebiliyor, tool sonucunu gözlemleyebiliyor ve gerekirse yeni bir adım atabiliyordu. Deployment aşamasında bu mantık korunur; değişen şey graph’ın çağrıldığı sınırdır. Artık graph, doğrudan notebook fonksiyonlarıyla değil, bir API istemcisi üzerinden çalıştırılır.

Yerel Studio’nun Rolü

Studio yalnızca görsel bir deneme aracı değildir. Yerelde çalışan bir geliştirme API’sinin üzerine kuruludur. SDK ile aynı yerel API URL’ine bağlanıldığında assistant kayıtları listelenebilir, thread oluşturulabilir ve graph run’ı stream edilebilir. Bu, deployment modelini üretimden önce yerelde sınamak için önemlidir.

Bulut Deployment’ın Rolü

Bulut tarafında temel programlama deseni korunur. Yerel http://127.0.0.1:2024 adresinin yerine deployment URL’i verilir; SDK yine assistants, threads ve runs üzerinden çalışır. Bu tasarım, graph kodunun çalışma ortamından bağımsız olarak çağrılabilmesini sağlar.

Kritik Soru

Bir agent notebook içinde çalışıyorsa neden API’ye taşınmalıdır? Çünkü üretim senaryosunda agent’ın başka uygulamalardan çağrılması, uzun süren run’ların yönetilmesi, state’in korunması, tracing/monitoring yapılması ve yetkilendirme sınırlarının belirlenmesi gerekir.

from langchain_core.messages import HumanMessage

# Input
input = {
    "messages": [
        HumanMessage(
            content="Multiply 3 by 2."
        )
    ]
}

# Stream
async for chunk in client.runs.stream(
    thread["thread_id"],
    "agent",
    input=input,
    stream_mode="values",
):
    if chunk.data and chunk.event != "metadata":
        print(chunk.data["messages"][-1])

Run streamGraph adımları state değerleriyle birlikte izlenir.

State’in Evrimi

Bu derste gerçek state alanı messages üzerinden izlenir. stream_mode="values" kullanıldığı için her graph adımından sonra state’in görünen değeri chunk.data içinde okunur.

Başlangıç

{"messages": [HumanMessage(...)]} graph’a giriş olarak verilir.

Model adımı

AI mesajı tool call metadata’sı üretir.

Tool adımı

multiply sonucu tool mesajı olarak eklenir.

Nihai state

AI cevabı mesaj listesine son yanıt olarak eklenir.

Agent / Tool Etkileşimi

Bu ders deployment odaklıdır; buna rağmen stream çıktısı önceki agent-tool döngüsünün API üzerinden de aynı biçimde yürüdüğünü gösterir. Modelin iç düşüncesi gösterilmez; yalnızca görünen mesajlar ve tool call yapısı izlenir.

Kullanıcı

“Multiply 3 by 2.”

AI mesajı

multiply aracı için {"a": 3, "b": 2} argümanlarını üretir.

Tool

Sonuç 6 olarak döner.

AI cevabı

Sonucu doğal dilde ifade eder.

Yaygın Hatalar

  • Studio’yu yalnızca görsel arayüz sanıp arkasındaki API yüzeyini gözden kaçırmak.
  • Yerel API URL’i çalışmadan SDK istemcisinin assistant listesini döndüreceğini varsaymak.
  • assistant, graph_id, thread ve run kavramlarını aynı şey gibi düşünmek.
  • stream_mode="values" çıktısını yalnızca model cevabı sanmak; bu mod state değerlerini adım adım gösterir.
  • API anahtarını kaynak koda yazmak veya HTML içinde açık bırakmak.
  • Bulut deployment’a geçince graph davranışının tamamen farklı bir SDK gerektirdiğini düşünmek.
  • Tool sonucunu nihai AI cevabı ile karıştırmak.
  • Assistant listesindeki indekslerin her ortamda aynı olacağını varsaymak.

Son Çıkarımlar

  1. Deployment, agent mantığını değiştirmekten çok graph’ı servis edilebilir bir API yüzeyine taşır.
  2. Studio, yerelde çalışan LangGraph API’yi kullanan bir geliştirme ortamıdır.
  3. SDK, yerel ve bulut API için aynı istemci desenini korur.
  4. Assistant kaydı çalıştırılabilir graph’ı temsil eder; graph_id run hedefini netleştirir.
  5. Thread, state geçmişinin izleneceği yürütme kapsamını oluşturur.
  6. Run stream çıktısı agent’ın adımlarını state üzerinden gözlemlemeyi sağlar.
  7. Tool call, tool sonucu ve nihai AI cevabı ayrı mesaj türleri olarak okunmalıdır.
  8. Bulut deployment için API anahtarı ortam değişkeni üzerinden verilmelidir.
  9. Yerel URL’den bulut URL’ine geçiş, SDK kullanım biçimini temelde değiştirmez.
  10. Üretim ortamında monitoring, tracing ve erişim yönetimi notebook deneyiminin ötesindeki temel ihtiyaçlardır.
